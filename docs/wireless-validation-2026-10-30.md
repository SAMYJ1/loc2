# 无 USB 的无线与纯蓝牙验证：2026-10-30

结论：**纯蓝牙本轮短暂采用了目标，但约 30–40 秒后回到真实位置，尚不能稳定使用；蓝牙＋Wi-Fi 组合未完成网络 CarPlay 建连，未进入位置供数验证。** 两项均不能标记为稳定无线定位成功。

## 条件与隔离

- 目标沿用赛银国际广场 WGS84 30.2771763 / 120.0158935，用户确认开始时为真实位置，定位服务开启。
- 不更改开发者模式，沿用此前开启状态。没有为测试降低网络加密或关闭 Mac 安全设置。
- 无线测试前后及运行过程中检查 USB 为零。中途仅为准确识别手机，用户临时接 USB，读取该机蓝牙地址后再次拔线；识别阶段没有报点。
- 蓝牙配对列表存在重复条目，旧记录地址不能直接复用。以该台有线可信手机返回的 BluetoothAddress 锁定目标，不根据同名设备随意选择。
- 用户授权只使用当前 Wi-Fi 对应的凭据。本轮从精确匹配的钥匙串记录读取，密码未显示或上传，临时配置和日志中的密码副本已清除。原钥匙串条目及原实验目录保持不变。

## 蓝牙＋同一 Wi-Fi

使用既有 MacPlay 无线后端及控制器，可见 CarPlay 模式；指定蓝牙位置通道，因为手机实际在该通道订阅。它与纯蓝牙定位不是一回事：该控制器还要求网络 CarPlay 视频就绪后才允许供数。

| 阶段 | 观察 | 判定 |
| --- | --- | --- |
| 最初准备 | 蓝牙 Unix socket 路径超过 macOS 长度限制，尚未开始协议 | 本机准备错误；改用短私有目录后解决，不计为无线能力失败 |
| 首次配对窗口 | 用户确认蓝牙/CarPlay 提示后，约 202 秒认证成功并收到蓝牙位置订阅，但 240 秒时网络会话仍未完成 | 未解码视频，零坐标发送 |
| 已配对后重试 | 约 7 秒认证和蓝牙位置订阅通过，仍无网络 control-connected 或首帧；约 187 秒接收器退出 | 零坐标发送，未进入位置采用判断 |
| 局域网可达性检查 | 用户用 iPhone Safari 打开 Mac 的临时只读 HTTP 页面，确认连接成功 | 基本 LAN 可达；不能据此保证 CarPlay 特定协议握手成功 |

Mac 防火墙检查结果为原本未开启，本轮没有修改防火墙。临时 HTTP 服务已停止。两次有效无线建连尝试的本地接受和位置消息入队均为零，不能写成“无线位置数据已送到但手机拒绝”。目前只确认了蓝牙控制部分，Wi-Fi 网络接管的具体阻碍仍未确定。

## 纯蓝牙独立实验

既有 MacPlay 配置要求 Wi-Fi，不适合声称纯蓝牙。本轮另行只读审查并使用独立实验客户端 [accessory-location](https://github.com/aur3l14no/accessory-location/tree/8a13296a3d81dae18ad4481e7a9eca913c2c644f)，固定提交 `8a13296a3d81dae18ad4481e7a9eca913c2c644f`。它的 Bluetooth profile 不声明无线 CarPlay，通过经典蓝牙 iAP2/RFCOMM 供给位置；不是普通 BLE App，也没有集成到 Location Lab 产品执行路径。

- 在仓库外隔离环境构建，先通过 37 项软件测试；使用已有本机认证材料，没有下载或生成新认证身份。
- 手机 Wi-Fi 由用户关闭，USB 保持拔出，Mac Wi-Fi 保留用于本机正常网络。
- 发送进程及认证子进程套用禁止 IP 网络的 sandbox profile；另以 loopback TCP 连接被拒绝验证约束生效。该限制不改变系统网络设置。
- 先进行 20 秒、不发坐标的探测：RFCOMM 通道 1、iAP2 协商、设备识别和认证均通过；未收到位置请求，发送为零。
- 随后进行 120 秒位置窗口：收到手机 GGA/RMC 请求后才发送，遵守订阅间隔；USB 每两秒复查，发现接线就结束测试。
- 用户先报告到达广场附近，随后在稳定性观察中报告 **约 30–40 秒后回到原来的真实位置**。
- 本轮结束时记录 102 个位置消息的链路 ACK，未出现连接异常退出或位置 Stop 事件，正常退出码为零。源码的发送函数会等待对应链路 ACK 后才返回，但 ACK 依然不证明每个坐标被定位系统采用。

该组合表明纯蓝牙可以建立认证位置链路并造成一次可观察的位置变化，但未通过持续稳定采用。期间 ACK 仍在继续而地图返回真实位置，使手机采用/解析层值得进一步检查；尚无手机原生来源字段或拒绝日志，不能直接断言具体融合或拒绝算法。

## 纯蓝牙再次切换到赛银国际广场

用户随后要求再次通过蓝牙切换到同一目标，复用相同实验客户端、认证材料和 WGS84 坐标，120 秒窗口。开始前及结束后 USB 均为零；发送进程继续使用禁止 IP 网络的隔离策略。本轮没有要求关闭手机 Wi-Fi，也未改变其网络或开发者模式设置，因此只验证位置供数走蓝牙，不将其他定位来源视为已隔离。

识别与认证通过，手机两次请求 GGA/RMC、两次停止位置请求；客户端据此暂停/恢复，最终获得 34 个位置消息的链路 ACK，正常到时退出。用户先确认蓝点到达广场附近，后续稳定性观察报告回到真实位置或发生跳动。结束后用户明确确认真实位置已稳定、定位服务开启；所有测试接收进程数为零。

这再次证明短暂位置变化可以发生，但未通过持续稳定采用。本轮存在位置 Stop，与前一轮“持续 ACK、无 Stop 却回到真实位置”的观察不同；未采集手机端原因日志，不能把两轮的回跳归结为同一种已证实机制。

## 已有配对后的纯 Wi-Fi 重连试验

用户要求仅 Wi-Fi。手机关闭蓝牙、USB 拔出，Mac 与手机保持同一 Wi-Fi；Mac 蓝牙保留给其他正常外设，但测试目录中的蓝牙桥接被明确禁用，没有实际桥接进程。

这不是普通 MacPlay 默认流程：独立目录允许网络发现先于蓝牙 handoff，并只接受此前从目标 iPhone 已验证会话取得的网络标识。helper 二进制保持相同，其他原资源未修改。未读取或提供 Wi-Fi 密码；尝试的是已入网、已有配对的网络重连，不代表首次纯 Wi-Fi 配对支持。

- 初轮发现 IPv6 多播接口格式错误。独立 UDP 复现中，旧格式返回 `EINVAL/EHOSTUNREACH`；使用 `::%en0` 后加入及发送均正常，与 [Node 官方接口作用域说明](https://nodejs.org/api/dgram.html#socketsetmulticastinterfacemulticastinterface)一致。只修正了独立测试目录。
- 修正后，IPv4/IPv6 发现就绪、广播和查询正常，但没有发现目标 CarPlay 控制服务，也没有入站控制连接。
- 三个窗口分别运行约 180.365、180.403 和 173.387 秒，认证、视频、位置订阅、接受批次和入队消息均为零。前两个到时结束，最后一个正常请求停止。
- 用户起初选择了“连接成功/有画面”，随后明确澄清：看到的是设备列表里的 MacPlay 条目，没有连接按钮。该条目不能视为实时 CarPlay 会话，以澄清与机器记录为准。
- 最终测试进程全部退出。用户随后要求重新测试 Wi-Fi＋蓝牙，并确认重新开启手机蓝牙。

结论：本次“无蓝牙引导，直接仅 Wi-Fi 建连”未成功，未进入位置采用测试。不能据此证明 iOS 或所有实现均不支持 Wi-Fi 位置传输，也不涵盖“先蓝牙完成建连，再仅用 Wi-Fi 传数据”的另一种流程。
