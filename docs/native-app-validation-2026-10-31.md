# 原生 App 实现与当前验收状态

更新：2026-10-31。对应 [Issue #10](https://github.com/SAMYJ1/toAnywhere/issues/10)。代码和安装均已推进，但新网络的无线建连与两小时验收尚未通过，不能将本文件视为整体验收完成。

## 已实现

- iPhone 原生地图、搜索、选点、收藏管理、最近使用、系统定位观测与恢复状态。
- 手机本地保存地点；Mac 不在线时仍可准备草稿。明确应用才启动会话。
- 扫码、Mac 首次批准、TLS 服务指纹校验、Keychain 持久凭据及撤销。
- Mac 默认后台运行，自启动可选；保留停止、网络检查、安装更新与诊断入口。
- 无线位置适配、隐藏真实视频解码、启动预热、私有短路径与进程清理。
- 当前 Wi-Fi 元数据自动更新；凭据按需从系统钥匙串读取，不在应用配置中另存 Wi-Fi 密码。运行时设置经匿名管道交给接收器。
- 换网结束旧会话；地址变化重建控制服务，不自动重放旧目标。
- 免费开发签名构建、无线安装、签名到期日期和续签说明、Mac 更新入口。

## 实际观察

1. 手机 App 已无线安装并打开；用户明确授权移除一个 UI 测试运行器以腾出免费签名名额，其他主应用和基准测试应用保留。
2. 用户已完成扫码及 Mac 批准，并确认手机显示连接就绪。
3. 一轮原生 App 观察测试实际接受163组、入队326条，解码638帧；用户确认 App 内系统蓝点到达西溪天街，并通过手机恢复操作回到实际位置。
4. 用户随后报告恢复界面未结束；修正恢复时限、基线与状态区分后，再次由用户确认收藏、应用、恢复短流程正常。
5. 上述原生短流程没有独立归档每轮实际网络名称和安全类型，不能将其当作 WPA2 与 WPA3 的严格对照。

## 已定位并修复的问题

| 问题 | 修正与证据 |
|---|---|
| 扫码提示“已取消” | 修正主机名大小写比较，补齐 TLS serverAuth EKU 与合适有效期；真实 Swift TLS 客户端验证正确指纹通过、错误指纹拒绝 |
| 长安装目录无法启动蓝牙桥 | 蓝牙 Unix socket 路径105字节超限；会话以短数据路径引用原身份，修复前集成测试失败、修复后通过 |
| 恢复界面无限等待 | 20秒后明确转为待确认；新鲜样本、已知来源及基线足够时才自动观测恢复；旧结论绑定会话版本 |
| 固定 Wi-Fi 配置失效 | 改为当前网络信息，取消应用密码文件；系统凭据接口4097改用标准钥匙串查询，当前网络无额外弹窗读取成功 |
| 停止标记写入竞态 | 完整序列化后原子发布，绑定会话和版本，避免读取半写文件或停止后来的目标 |
| TLS 接受线程被慢握手阻塞 | 握手移入受限工作线程，保留超时 |
| IPv6 发现地址作用域错误 | 数字 zone 改为所选接口名；缺失目标 TXT 时不探测未知手机；多播失败不再声称接口就绪 |

IPv6 修正使用真实运行时的 discovery 模块进行离线回归：修正前失败，修正后三项通过，全程没有网络 I/O。它解释了代码中的 IPv6 错误，但尚未在新网络重新真机验证，不能宣称连接问题已全部解决。

## 2026-11-01：网络初始化与后续免交互读取

用户报告每次连接前出现“Location Lab 想要进行更改”的管理员密码框，要求改为初次初始化确认、后续复用。

旧实现重启后重新读取系统 `AirPort` 凭据，只有内存缓存，并使用 `kSecUseAuthenticationUIFail` 抑制弹窗。该参数不能可靠抑制文件式钥匙串的交互；[Chromium 的对应兼容实现](https://chromium.googlesource.com/chromium/src/crypto/+/refs/heads/main/apple/scoped_keychain_user_interaction_allowed.cc)明确记录了这一限制。

新版将当前 SSID 的凭据保存到用户默认钥匙串中应用自己的服务条目。后续连接和进程重启优先读取该条目；自动读取会在受控作用域内禁用钥匙串交互并恢复原设置，不会自行弹管理员密码框。只有用户主动点击“初始化或更新网络授权…”才允许交互读取系统 Wi-Fi 凭据。没有将 Mac 登录密码写入应用，也没有修改系统 Wi-Fi 条目的访问控制。

新网络首次读取、网络密码变更、钥匙串锁定或访问权限被撤销需要明确处理，不能承诺绕过系统保护。构建脚本默认沿用已有应用签名身份，避免普通更新改变应用的钥匙串身份。

验证：初始化后模拟重启且系统项不可读的回归先失败、修正后通过；真实钥匙串使用独立测试条目跨进程写入／读取两次并清理通过；Python 64 项测试通过。新版已安装，签名 designated requirement 与更新前一致。用户完成当前网络的一次初始化后，应用专属条目已建立；随后实际重启 Mac 应用，控制 epoch 变化且状态新鲜，网络自动恢复就绪（`connectionHint=null`、`networkIssue=null`），没有再次要求用户输入密码，也未启动定位会话。

## 2026-11-01：远距离目标的系统筛选证据

用户报告约 10–20 公里目标难以采用，并询问提高频率是否有效。按用户请求采集绑定手机的 `locationd` 日志；实测设备为 iOS 27.0（24A435），本次直接查询 Developer Mode 为 enabled。用户选择“萧山人民广场”，保持 App 前台、不切点、不刷新定位服务；实际报点约 90 秒后由观察脚本绑定本轮会话停止。

- Mac 本地接受 87 组，入队 174 条，视频解码 88 帧；不是连接未完成。
- 手机记录 87 次 `CLNmeaScreener,screen` 决策，每次对应 `GPRMC NMEA Screening failed`，共 87 次失败。
- `posDiff` 为 23083.46–23132.52 米；所有决策的 `positionDiffBound` 均为 15000 米。日志明确显示 `accessory location screening failed`，说明本轮外部位置已到达手机，但没有通过与系统参考位置的一致性筛选。
- 87 条 RMC 的报点时间戳差值为 82 次 1 秒、4 次 2 秒；没有出现提高频率后的对照试验，当前仍保持原频率。
- 用户确认蓝点始终没有到达目标。停止原因为 `local-stop`，接收器、helper、蓝牙桥及日志采集进程均已结束。

本轮证据不支持靠单纯加大发送频率解决：频率并不消除这次超出筛选界限的位移差；现有 `_nmea` 还只编码整秒 UTC，直接提高调度频率会生成同秒重复时间戳。没有修改频率或自动执行其他目标。15000 米仅是本轮观测值，不是 Apple 公布的通用距离上限，也不能据此保证所有 10 公里目标一定成功。若要解释更近目标的失败，需要对应轮次的筛选日志，不能把所有采用失败归为同一阈值。

原始定位日志及仅含筛选数值的汇总留在本机私有诊断目录，未将系统参考坐标、设备标识或认证资料提交到仓库。
