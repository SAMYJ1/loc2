# 隐藏模式修复与附近点验收：2026-10-30

结论：**修复运行目录中的模块身份分离后，loc2 隐藏模式本轮成功采用赛银国际广场附近点；用户确认无 CarPlay 投屏窗口，应用正常停止后拔线自动恢复真实位置。** 本轮为短时、固定点、开发者模式开启条件下的验证。

## 条件

- 沿用[可见模式成功轮次](saiyin-validation-2026-10-30.md)的 WGS84 30.2771763 / 120.0158935、helper 和配对身份。
- USB 单设备，开始前直接查询开发者模式为 `enabled`。没有改变手机安全或网络设置。
- 从 loc2 原生界面点击应用、采用确认、停止和恢复确认；目标是隐藏 CarPlay 画面，应用自身详情窗口可保留。

## 首轮失败与最小复现

旧隐藏目录下，应用停在“正在准备定位会话”，本地接受批次为零。正常点击停止后清空目标，接收进程为零，测试保护机制未触发。由于尚未供数，这轮不是手机拒绝目标位置的证据。

随后运行不发送坐标的连接诊断：认证、订阅、控制连接和视频包均出现，但 60 秒内没有解码就绪回调。只读模块解析发现：

- 主循环加载准备目录自己的 `media.js`。
- `protocol` 软链接回原目录，`cpStack.js` 的 `require('../media')` 因 Node 的真实路径解析而加载原目录的另一份 `media.js`。
- 接收视频和保存 decoder 的模块，与轮询就绪并持有回调的模块不是同一实例。

一次不加载原生库的 Node 解析检查直接返回 `sameMediaModule=false`；新增准备 CLI 回归从协议模块和顶层依赖触发回调，修改前收到零个事件，无法到达主模块。该反馈可以离线稳定复现，不需要反复操作手机。

## 修复

准备工具将白名单顶层 JavaScript 和 protocol 下的 JavaScript 复制到同一个私有 engine 目录，保留二进制、媒体库及 node_modules 的受控链接。这样协议层与主循环共享同一份隐藏 media 模块。非 JavaScript 的 protocol 文件不复制，认证资料仍由本机独立准备。

修复没有改动原实验资源，未重编译 iAP2 helper，也不需要重签名应用。旧准备目录保留作诊断，实际应用明确切换到新生成的私有目录。

## 验证

- 准备 CLI/Node 回归：修改前失败，修改后通过；两条路径的回调都到达同一个准备模块。
- 实际运行目录解析检查：`sameMediaModule=true`；JavaScript 语法检查通过。
- 不发送坐标的真机诊断：约 3.524 秒首帧解码，随后 `showCarPlay=false`、`hiddenVideoValidation=true` 和适配器 `video-ready`；约 5.248 秒记录收到/解码均为 65 帧，零次恢复；没有发送位置命令，约 7 秒结束清理。
- 从应用重新应用广场目标后，界面正常进入报点。用户确认蓝点到广场附近并保持稳定，且没有出现 CarPlay 投屏窗口。
- 根据用户观察点击“已观察到目标位置”，界面记录采用已确认；当时最近可见本地接受批次为 134，这不是手机 ACK 或最终总计。
- 点击应用“停止报点”，目标清空；接收器与 helper 进程数为零，测试保护时限被取消而未触发。
- 用户确认拔线等待后自动恢复真实位置，没有开关定位服务；应用随后记录“恢复：用户已确认”。
- 全量 43 项 Python 测试通过，`git diff --check` 通过。

## 结论边界

这次证明了该模块图缺陷造成的隐藏模式准备阻塞可以被修复，并完成本条件下的短时位置修改与恢复。它不解释此前老链路的远距离目标间歇失败，也不证明任意距离、长时间运行、锁屏、关闭开发者模式或所有应用都可用。

本机当前配置保留修复后的隐藏运行目录。精确真实位置、设备标识、认证材料与诊断原始内容未加入仓库。
