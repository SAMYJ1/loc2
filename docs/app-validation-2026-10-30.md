# loc2 应用验收：2026-10-30

结论：**原控制器成功之后，改用 loc2 应用界面的定位测试仍未通过位置采用验收。** 本记录不把本地接受计数当作手机采用证据。

## 实际测试入口与条件

- 从已构建的 loc2 原生界面输入 WGS84 31.2304 / 121.4737，点击“应用位置”；由打包的 Python 会话服务和 USB 适配器启动接收器。
- 测试前直接查询开发者模式为 `enabled`；用户确认上次测试已恢复真实位置。
- 采用原成功组的 CarPlay 身份及认证文件。helper 与基础 engine 文件哈希和刚成功的原控制器轮次一致。
- 先用隐藏视频覆盖，再切换为原可见视频资源；两者使用相同私有数据目录。未修改原实验目录。
- 测试使用额外的 180 秒保护机制：超时会终止本机服务，由其清理 USB 子进程。该机制仅用于本轮验收，不是产品的持续策略。

## 观察结果

| 条件 | 应用行为 | 手机观察 | 结束方式 |
| --- | --- | --- | --- |
| 原应用逻辑＋隐藏模式 | 进入报点；界面最后可见本地接受 143 批 | 用户确认始终是真实位置 | 测试保护时限结束本机服务；接收进程数为零 |
| 原应用逻辑＋可见模式 | 订阅暂停后恢复，停止前最近界面读数为 105 批 | 用户确认仍是真实位置 | 从界面点击“停止报点”，显示已停止并清空已接受目标；接收进程数为零 |
| 等待视频就绪的新逻辑＋可见模式，权限尚未满足 | 接收器启动阻塞，未进入正常会话 | 不作位置采用判断 | 保护时限结束服务 |
| 等待视频就绪的新逻辑＋可见模式，处理文稿访问后 | 启动恢复，进入报点；最后可见本地接受 121 批 | 用户确认仍是真实位置 | 保护时限先于界面停止操作结束服务；接收进程数为零 |

在隐藏轮次尝试只读检查接收器窗口时，工具未成功返回窗口状态，因此不能将其作为“完全没有可见窗口”或“视频持续解码”的独立证明。

## 已定位的启动阻塞

原运行资源仍通过符号链接指向旧 Documents 目录。接收器进程采样显示停留在 `dyld` 动态库加载的 `__open`，尚未进入引擎正常会话代码。系统 TCC 日志随后明确出现 `local.loc2.app` 的 `SystemPolicyDocumentsFolder` 权限请求，并提示新构建的代码要求与既有记录不匹配。

用户选择在 Mac 上允许 loc2 访问“文稿”目录；保持该构建后重开，应用恢复正常启动。未申请或开启完全磁盘访问权限，也未修改 iPhone 开发者模式。

## 供数时序变更及验证

回归测试确认：原应用在收到认证和位置订阅后、尚未收到视频就绪信号时就供数。原控制器成功流程则在视频首帧后 arming。

应用现将可见模式的 `showCarPlay=true` 或隐藏覆盖的 `hiddenVideoValidation=true` 作为当前会话的视频就绪信号，只有认证、该信号和真实订阅都满足才供数；停止、断线或新会话会清除就绪状态，旧会话事件不能放行新会话。原生和手机页面显示相应等待状态。

- 新回归在修改前失败、修改后通过。
- 42 项 Python 测试通过，包含真实适配器对可见/隐藏两种就绪消息的边界测试。
- 手机首次配对、草稿隔离、应用与停止浏览器回归通过。
- 原生应用构建、签名及 `git diff --check` 通过。

**这项改动只对齐启动时序，真机复测仍未观察到位置采用，不能称为定位修复。** 权限处理与代码时序修改都发生在后续轮次，不能据结果独立确定各自对位置采用的影响。

## 剩余范围

应用位置修改仍未通过。下一步需要采集并对照应用实际供数及运行环境的脱敏证据，与原控制器成功轮次比较；不能继续仅以 UI 计数判断。A/B 切点、锁屏、手机网页真机控制和隐藏视频持续性也尚未验收通过。

本机测试配置当前为可见视频对照资源。记录中的运行时、配对资料与诊断文件均保留本机，未上传认证材料或设备标识。

## 后续对照对归因的限制

用户要求先确认老链路是否稳定。随后在相同版本、身份和开发者模式开启状态下，老链路两轮也均未观察到位置采用，见[老链路复查记录](device-validation-2026-10-30.md)。因此，本文件中的应用失败仍然有效，但不足以证明失败由 loc2 独有问题造成；应用侧归因暂停，等待建立可靠对照。

后续将目标改为用户指定的赛银国际广场附近点后，老链路及应用可见模式均成功采用，应用正常停止和拔线后恢复也有观察证据，见[附近点成功对照](saiyin-validation-2026-10-30.md)。因此本页的失败结论仅限此前远距离目标和具体轮次，不应扩展为应用在所有条件下不可用。
